# AI 协作过程记录与复盘

## 一、协作规则（先定规矩，再让 AI 动手）

1. **先澄清需求**：不直接把题目丢给 AI，先写 `需求分析.md`（目标、输入输出、边界、验收标准）。
2. **分模块、小步走**：按 M0→M6 拆解，每次只让 AI 完成**一个模块**，并限定只能改动的文件。
3. **每步立即验证**：每个模块完成后立刻跑单测，不通过不进入下一个模块。
4. **限制重构范围**：明确告知"不要顺手重构其他文件"。
5. **关键节点人工接管**：金额舍入口径、清洗顺序、并发方案、错误码口径由人工拍板。

交付顺序按 `需求分析.md` 中的 M0~M6 执行，最后才集成。

## 三、人工 Code Review 发现并修正的问题（AI 初稿不能直接用）

| # | 问题 | AI 初稿的表现 | 人工判断与修正 |
| --- | --- | --- | --- |
| 1 | pydantic 字段名与类型名冲突 | `date: date` 直接导致导入报 `PydanticUserError` | 改为 `date: dt.date`（`import datetime as dt`），保留对外字段名仍为 `date` |
| 2 | 金额"四舍五入"口径 | 直接用 numpy 默认舍入（银行家舍入，`1.005→1.0`） | 改为 `Decimal + ROUND_HALF_UP` 实现真正的四舍五入，并加单测固化 |
| 3 | 脚本入口缺失 | `report_gen.py` 没有 `if __name__ == "__main__"`，`python -m src.report_gen` **静默无输出**（退出码 0 但什么都没发生） | 补入口并跑真实命令复核，避免"看起来跑通了其实没跑" |
| 4 | 废弃 API | 使用 `status.HTTP_422_UNPROCESSABLE_ENTITY`，产生 DeprecationWarning | 改为数值 `422`，避免依赖版本差异 |
| 5 | 依赖未装齐 | 声称已装 uvicorn，实际 `No module named uvicorn`，冒烟脚本超时 | 人工核对导入，补装 uvicorn 后重跑通过 |
| 6 | "原始文件不得修改"缺少证据 | 只有"用只读方式打开"的口头保证 | 增加 MD5 前后比对测试（`test_端到端_生成报表且原始文件未被修改`） |

> 结论：AI 产出必须逐模块运行验证，"跑通"要有人工可复核的证据，不能只看代码是否通顺。

## 四、风险识别与人工审查

| 维度 | 风险 | 处理方式 |
| --- | --- | --- |
| 数据一致性 | 金额浮点误差导致统计与人工核对不一致 | 统一用 Decimal 舍入到 2 位；用三种维度汇总互相校验（合计均为 6450） |
| 数据安全 | 误写覆盖原始文件 | 只读读取 + MD5 校验测试 + 输出走独立目录 |
| 边界健壮性 | 缺列 / 空表 / 全为脏数据导致崩溃 | 自定义异常（`ReportError` / `MissingColumnsError` / `NoValidDataError`），CLI 返回退出码 1 并打印可读错误 |
| 并发一致性 | 并发写入产生脏数据或丢数据 | `BEGIN IMMEDIATE` + WAL + `busy_timeout`；用 8 线程 40 次写入做验证 |
| 输入校验 | 非法参数被放过 | pydantic 模型集中校验（金额>0、类型枚举、日期格式、分页上限），非法参数返回 4xx 结构化错误体 |
| 合规 | 引入不必要依赖或使用未经许可的数据 | 只使用题目允许的库；样例数据自行构造，不含真实个人信息 |

## 五、分工：哪些交给 AI，哪些自己拍板

**交给 AI**：样板代码与目录骨架、pandas 聚合写法、SQLite 连接与事务样板、测试用例的批量铺开、文档初稿。

**自己拍板**：
- 需求歧义（关键字段范围、清洗顺序、金额精度、多月份的处理方式、错误码口径）；
- 清洗规则的顺序与语义（顺序不同结果不同）；
- 金额舍入必须"四舍五入"而非银行家舍入；
- 并发方案的取舍（SQLite 事务 + WAL 而非内存字典）；
- 验收口径与"证据"形式（MD5 校验、真实进程冒烟、可核对的汇总数值）。

## 六、复盘

**做得好的地方**
1. 先澄清再写码：把"关键字段有哪些""清洗顺序"这类歧义提前敲定，避免了返工。
2. 小步验证：每个模块独立跑测试再前进，问题（如 pydantic 冲突）在设计阶段就暴露，没有拖到最后集成。
3. 关键数值人工核对：报表总额、按销售员/地区/月份三种口径交叉验证一致。
4. 对 AI 输出做了实质 Review，抓到"静默不执行"这类隐蔽问题。

**可以做得更好的地方**
1. M0 时没有第一时间确认运行环境（本机默认 `python` 是 3.6，需改用 3.13，uvicorn 还漏装），浪费了少量时间。**教训：先确认环境再动手。**
2. 早期只覆盖正常路径，异常用例是在 M4 才补齐的；如果 M1 就同步补异常用例，验证会更早闭环。
3. 清洗规则目前把"数量为文本"也当作缺失处理，这一口径虽合理但需求未明确，已通过文档与单测显式固化，若评审有异议可快速调整。

**总体自评**：AI 承担了约 70% 的编码量，但需求定义、规则拍板、数值核对、错误修正与验收证据均由人工完成；过程按 M0~M6 分步留痕，可追溯、可复现。
